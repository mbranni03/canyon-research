# Codex “Working / Worked for…” conversation disclosure

Codex groups intermediate assistant activity into a disclosure above the final answer. The collapsed row preserves a short work status and, when available, elapsed duration; expanding it reveals the underlying activity. This lets a reader scan the request and answer without scrolling through every progress update and tool step.

**Status:** behavior specification reconstructed from packaged JavaScript, with implementation recommendations explicitly marked. **Inspected:** October 19, 2026; desktop version **26.1013.40934**, build **20770**, bundle identifier `com.openai.codex`. The installed bundle is named `ChatGPT.app`; this document concerns its Codex conversation components. Static inspection establishes code paths, not their execution or rollout for every account. No live conversation, user database, or network traffic was inspected.

For a custom application backed by Claude Code, see the [JSON-stream implementation spec](../claude-code-multitask/working-disclosure-implementation-spec.md). It adapts this presentation pattern while making Claude's different completion and timing signals explicit.

## Scope

The feature is a presentation layer over a conversation turn. Collapsing activity changes what the conversation renders; it does not summarize, delete, compact, or rewrite the model's context. The final answer remains a separate conversation item. A disclosure can contain intermediate prose as well as tool activity, so it is broader than a tool-call log.

This specification separates the packaged implementation from proposed requirements for a reconstruction. Where a rule depends on route configuration or a supplied status item, reproduce that distinction instead of assuming one universal default. The full turn-level disclosure belongs to the `all` activity mode. A separate `latest` mode trims completed tool groups and retains recent commentary/current activity; it is not simply the same disclosure with a live preview.

## Visible layout

```text
User request

  › Worked for 42s          ← collapsed activity disclosure

Final assistant answer     ← outside the disclosure
```

Expanded, the same region reveals its activity in conversation order:

```text
User request

  ⌄ Worked for 42s
      Intermediate assistant update
      Tool activity and its rendered details
      Further intermediate activity

Final assistant answer
```

These are schematic layouts, not pixel-accurate screenshots. Labels and duration units are localized.

## What folds and what stays visible

The main user prompt precedes the activity section. Intermediate assistant commentary and tool activity can enter the collapsible region. Grouping is based on message type and renderer policy, not a text-length threshold or a summary generated by the model.

Some content remains visible even when other activity folds:

- The qualifying final assistant answer.
- Incomplete user-input responses and the specific MCP error that approval is required while approval policy is `never`.
- Dynamic renderers that opt into `persistentInCollapsedConversation`, and MCP app widgets when the applicable option requests it.
- Pending steering, unsent user messages, hook feedback, and mid-turn user messages with no following final answer. A mid-turn user message followed by a final answer can instead be folded.

Approval, user-input, elicitation, and permission-request items are separated into their own turn outputs. Do not assume every interaction is an ordinary hidden tool row. This list describes the inspected grouping rules; it is not a guarantee about every extension renderer.

## Collapse lifecycle

The main turn renderer requires both renderable activity and permission to collapse it. In the ordinary local-conversation route, automatic collapse becomes eligible when the final assistant answer has started and the turn is not cancelled. A route can separately allow collapse before the final answer; an activity-context route also prevents automatic collapse while work is running.

When eligible, the section defaults to collapsed unless automatic collapse is prevented. An explicit remembered disclosure choice overrides that default. A forced-expanded state or disabled-collapse setting takes precedence over the remembered choice. Expanding the section exposes the existing activity; collapsing it restores the compact row. The component has a mounted React-state fallback and accepts externally supplied collapsed state/change handling. The inspected scope does not establish reload persistence.

Starting the final answer is the relevant transition: the implementation does not need to wait until the full answer finishes streaming. Do not treat every assistant message as a final answer. The inspected predicate requires the final-answer phase and excludes asynchronous delivery and asynchronous user-input requests. It also requires nonempty content, a completed message, or structured output: an empty unfinished message with no structured output does not qualify, while an empty completed answer can. Cancellation blocks the ordinary collapse condition, but an explicit pre-final-collapse route and structured/terminal activity handling can take a different path; cancellation is not a universal force-expanded rule.

## Work status and elapsed time

The dedicated disclosure supports a structured work-status item and an older duration-only fallback. The status item determines the label; the presence of a folded section alone does not imply successful completion.

| State/input | Label behavior |
|---|---|
| Working, elapsed under one second | `Working` |
| Working, elapsed at least one second | `Working for {duration}` |
| Structured `worked` status | `Worked for {duration}` |
| Stopped | `You stopped after {duration}` |
| Paused | `Paused` |
| Explicit `unknown` status | `Activity` |
| Loading state | Loading presentation; do not invent a duration |
| Legacy duration supplied | `Worked for {duration}` |
| No structured status or legacy duration | `{N} previous messages` |

For the structured status item, elapsed milliseconds are `max((completedAtMs ?? now) - startedAtMs, 0)`. A working item without a completion time refreshes its clock every second. A completion timestamp fixes the end time. Duration formatting floors to whole seconds, uses localized narrow units, and omits zero-valued units: for example, English output can use `1m` at sixty seconds and `1h` at sixty minutes. Completed sub-second durations format as zero seconds. These examples describe duration formatting; exact sentence punctuation and units depend on locale.

In ordinary normalized turns, work starts from the turn-start timestamp, falling back to the first work-item start. The completed endpoint is the start of the final assistant answer, so the reported work duration excludes time spent streaming that answer. A turn can therefore have a `worked` activity item while its final answer is still streaming. Generation of that status item is suppressed for sleep-containing turns and for completed turns lacking the required first-work timing input.

The label renderer supports more statuses than the ordinary turn generator emits. In particular, the normal cancelled-turn generator can produce `unknown` (`Activity`), while a separate client-interruption compatibility branch creates `stopped`. A stopped label is not the universal label for every cancellation.

## Disclosure interaction and secondary indicators

The disclosure control toggles expansion, updates `aria-expanded`, and rotates its chevron. The expanded body uses a height/opacity transition with a reduced-motion branch. Eligible reasoning content can preload on focus or pointer hover in an invisible, inert container; this is preparatory rendering, not visible expansion.

When a turn has auto-review denials, the row also shows a historical denied-action count and explanatory tooltip. A later approved retry does not erase a past denial from that count. Opening through that indicator can scroll to denial details after expansion; reduced motion selects instant scrolling.

The fallback count counts items inside grouped activity, plus inline subagent content when present; it is not simply the number of rendered rows. An empty activity section and a section containing only context compaction do not get a normal disclosure toggle.

## Requirements for a reconstruction

The following are proposed implementation requirements, not additional claims about Codex internals:

1. Keep an ordered, lossless activity collection keyed to its turn. Treat the folded view as a projection of that collection.
2. Keep the main user prompt and final answer outside the activity region. Apply explicit grouping rules to mid-turn user messages and persistent items. Preserve actionable input and approval controls wherever their actual rendering path places them; never make required interaction inaccessible inside a closed region.
3. Track execution status separately from disclosure expansion. Expanding activity must not resume, cancel, or restart work.
4. Preserve the user's explicit disclosure choice across streaming updates in the same mounted conversation. Define reload persistence explicitly rather than assuming Codex's remembered state is durable storage.
5. Derive duration from stable timestamps. Never add a second on each render, reset elapsed time on expansion, or label an interrupted run as successfully completed.
6. Use a keyboard-operable disclosure control with an accessible name, `aria-expanded`, and an associated content region. Maintain focus when activity is added or removed from the visible layout.
7. Keep scroll position stable for readers inspecting earlier content. New activity should not repeatedly pull them to the bottom. Honor reduced-motion preferences for any animation.

## Acceptance scenarios

These scenarios specify what to verify when implementing the feature. They are not claims that an end-to-end Codex test was run.

| Scenario | Expected result |
|---|---|
| Ordinary turn streams commentary and tools before a final answer | Intermediate activity remains available; ordinary automatic collapse is not yet eligible. |
| Final answer begins streaming with prior renderable activity | Eligible activity defaults to collapsed unless an override prevents it; final answer stays visible outside. |
| No renderable activity precedes the answer | Do not manufacture an empty disclosure. |
| User expands an eligible folded section | Reveal activity in order, leaving the answer outside; streaming updates do not discard the explicit choice. |
| A force-expanded or disable-collapse override applies | Keep the activity expanded even if the default or remembered state would collapse it. |
| Working elapsed is 999 ms, then 1,000 ms | Transition from `Working` to a duration-bearing working label. |
| Elapsed reaches exactly sixty seconds | Display localized minute output without a zero-second suffix. |
| Clock/end timestamps produce a negative interval | Clamp elapsed time to zero. |
| A structured completed item has a completion timestamp | Freeze duration at that timestamp; use the completed label. |
| A final answer takes additional time to stream | Keep its work endpoint at final-answer start; do not add answer-streaming time. |
| A structured stopped item is rendered | Use `You stopped after…`; do not imply success. |
| Structured status is paused, unknown, or loading | Show the matching paused, activity, or loading presentation without inventing a work duration. |
| A route permits collapse before the final answer | Allow eligibility before the final boundary when renderable activity exists; still apply expansion overrides. |
| Activity-context work is still running | Its prevent-auto-collapse setting keeps the default expanded unless an explicit state/override takes precedence. |
| A cancelled ordinary turn has no final-answer collapse transition | Do not assume it follows the successful turn's automatic-collapse path. |
| A final-looking message has asynchronous delivery, or is empty and unfinished without structured output | Do not use it as the qualifying final-answer boundary. |
| A final-phase message is empty but completed | The content/completion predicate can still accept it; apply the other final-answer guards. |
| A mid-turn user message is followed by a qualifying final answer | It can join folded activity; pending steering, unsent messages, hook feedback, and messages without a following final stay visible. |
| A persistent renderer or separate approval/input output is present | Keep it accessible according to its grouping contract when other activity folds. |
| Activity display mode is `latest` | Use its trimming behavior; do not assume the `all` mode disclosure is mounted. |
| Only a legacy duration is available | Use the duration fallback; when absent, use the previous-message count fallback. |
| Only context compaction remains in activity | Do not show a normal disclosure toggle for that lone item. |
| Auto-review denied an action and later approved a retry | Preserve the historical denial count; verify the indicator opens the relevant details. |
| Keyboard and screen-reader use; reduced-motion enabled | Verify the proposed accessibility and motion requirements independently. |
