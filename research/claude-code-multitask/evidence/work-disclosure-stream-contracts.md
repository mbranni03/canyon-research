# Work disclosure: Claude stream contracts and design boundary

Checked October 19, 2026. This is official-source research for a proposed raw Claude Code CLI integration, not reverse engineering of Claude internals or a live integration trial. Read-only `claude --version` returned **2.1.303 (Claude Code)**; `claude --help` was also invoked. No prompt, model request, authentication command, session transcript, or user profile was accessed. Public SDK declarations below describe the published protocol; they do not prove compatibility of this installed executable with a particular SDK package.

## Source ledger

**C1 — [Programmatic CLI](https://code.claude.com/docs/en/headless).** The documented token-stream launch uses `-p`, `--output-format stream-json`, `--verbose`, and `--include-partial-messages`. Output is newline-delimited JSON. `parent_tool_use_id` distinguishes main messages (`null`) from child messages. Child text forwarding is optional; nesting follows the spawning tool IDs. Retry notifications use `system/api_retry`. SIGTERM exits with 143 without completing the in-progress turn or recording its result; SIGINT ends the turn before process termination. Background work can keep a print-mode process alive.

**C2 — [CLI flags](https://code.claude.com/docs/en/cli-reference).** `--permission-prompt-tool` selects a loaded MCP permission tool. `--permission-prompts none` denies unresolved prompts instead of waiting for a permission host. `--replay-user-messages` acknowledges stream-JSON input on stdout. `--resume` continues a named session. These flags are interfaces to existing process and permission integration, not reasons to add a control protocol to a presentation feature.

**C3 — [SDK streaming](https://code.claude.com/docs/en/agent-sdk/streaming-output).** Partial wrappers contain raw API events; accumulate deltas. Current documentation says token-level partials are main-session only; child attribution uses complete messages. Complete `assistant` frames arrive per nonempty content block, often sharing an API message ID, before that block's stop event. A block stop closes input generation, not execution. A message stop closes one response, not the tool loop. Cut streams can still emit message stop. Structured output is validated only in the terminal result.

**C4 — [Published Anthropic SDK 0.3.301 declarations](https://app.unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.301/files/sdk.d.ts).** Inspect `SDKAssistantMessage`, `SDKPartialAssistantMessage`, `SDKUserMessage`, `SDKResultMessage`, `SDKResultSuccess`, and `SDKResultError`. Result is the turn-complete signal, with informational events allowed afterward. Success subtype still requires checking `is_error`: it can contain API error text. Early-stop subtypes include execution, max-turns, budget, and structured-output-retry errors. User-role frames commonly carry tool results. Assistant envelope UUID and API message ID are separate identities; no Codex-style final-answer phase is documented in these message declarations.

**C5 — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions) and [user input](https://code.claude.com/docs/en/agent-sdk/user-input).** `canUseTool` belongs to the SDK, pauses pending approval/question handling, and is not a callback exposed by merely parsing raw CLI stdout. Permission mode and earlier rules affect whether a host is consulted. Keep app-owned pending interactions visible; do not infer a pending approval from an ordinary tool-use block.

**C6 — [API streaming](https://platform.claude.com/docs/en/build-with-claude/streaming).** Indexed block starts/deltas/stops describe text and tool-input generation. `input_json_delta.partial_json` is incomplete JSON until accumulated. Stop reasons belong to a response, which can request more tools. Ping and error handling must not produce false assistant text or success.

**C7 — [Thinking documentation](https://platform.claude.com/docs/en/build-with-claude/thinking).** Returned thinking can be summarized and varies by configuration/model. Render only content actually exposed by supported blocks; signatures and encrypted/redacted data are not readable explanation text. The UI must not promise disclosure of private model reasoning.

## Recommended application policy (not a Claude protocol guarantee)

Use the existing CLI launcher, permission integration, storage, and frontend channel. One app request ID owns one turn. Use subprocess generation and a receive sequence to prevent late events from crossing turns. Stream-JSON stdin is optional; a single prompt argument is sufficient. Do not add task tools, a scheduler, SDK dependencies, or a new MCP server solely for this disclosure.

Keep an ordered activity log plus a provisional answer projection. Accumulate partials by root API message ID and block index; retain canonical complete blocks separately by envelope UUID and arrival order. Show the partial projection while streaming and prefer the assembled canonical blocks at message stop/result when available; never concatenate both projections. Deduplicate envelope UUIDs within session and process generation; multiple frames sharing only `message.id` are not duplicates. Without partials, retain complete block fragments by envelope identity and order. Preserve partial text if the stream ends abruptly before canonical blocks arrive. Do not collapse identical text blocks merely because their text matches.

Assign every ingested line a local stream sequence before journaling it. Reducer replay skips already-applied sequences in that process generation. Where partial wrappers lack a reliable UUID, apply live deltas once in order and use the journal sequence for replay. Never hash-deduplicate delta text: repeated tokens can be intentional. Reconnection without a reliable persisted cursor or original sequence is a new generation, not permission to append an ambiguous replay to an existing partial buffer.

The newest root message's text is visible immediately outside activity as a **candidate**, never as proven final text. Mark it ineligible on a root tool-use block, retry, error, or superseding root response. Move ineligible text into activity without losing it. Child text stays nested under its spawning tool and cannot become the parent answer. Do not use prose wording, elapsed silence, first text, `end_turn`, or `message_stop` as final classification.

On `result/subtype=success` with `is_error=false`, render `result.result` verbatim as the final answer. If it uniquely equals the latest eligible root response's complete concatenated text, associate the stored first nonempty text receipt timestamp. Otherwise retain the authoritative string independently and record final-start timing as unknown. Do not trim or fuzzy-match. Empty or structured-only results require an explicit empty/structured answer path.

Keep `Working` and its live timer until terminal confirmation. With proven mapping, freeze the reported work interval retrospectively at candidate text start, excluding answer streaming. Otherwise freeze at result receipt and label its diagnostic provenance as a run-end fallback. Error, cancellation, EOF, parse/transport failure, and missing-result exits freeze at their observed terminal time and remain distinct from successful completion. Result timing fields are not a documented substitute for the answer boundary. Prefer monotonic elapsed offsets during one process; persist timestamps and provenance for reloads.

Default auto-collapse to confirmed successful completion when renderable activity exists. This deliberately trades Codex's phase-driven early collapse for reliable raw-stream classification. Optional early candidate collapse is a separate policy: retain Working status and reverse the default on candidate demotion, while preserving explicit user expansion. Interaction state, spinner state, and task status remain separate. Tool failures and denials can remain in history while the overall run later succeeds.

For a text-only turn, show a noninteractive Working status while waiting, then remove it on success if no activity remains; never manufacture an empty disclosure. Manual collapse during work is allowed, with candidate text and pending app-owned interaction controls visible outside. Existing task cards may be activity, but task creation is not a prerequisite.

## Required fixtures and optional live validation

Verify text-only and tool-first turns; commentary then tools then answer; text and tool blocks sharing a message ID; assistant-before-block-stop ordering; identical text blocks with distinct identities; partial plus complete duplicates; child text and nested children; retries; result success with `is_error=true`; all documented early-stop subtypes; interruption and exit without result; unmatched/empty/structured final results; arbitrary byte chunks, split UTF-8, multiple lines per chunk, and a final unterminated line. Replaying persisted adapter envelopes must reproduce the same projection and timing. Reconnect should use a stored sequence cursor: do not guess duplicate unidentifiable delta chunks.

Before release, optionally capture sanitized streams from the pinned CLI using harmless text-only and read-only tool prompts with existing authentication and permissions. Validate candidate/result matching, child forwarding, signals, permission events, and result ordering. These workload trials were **not run** for this research. Documentation and declarations establish intended shapes, not executable ordering or timing guarantees beyond their stated contract.
